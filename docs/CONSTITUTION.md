# 工程宪法 / Engineering Constitution

**版本 1.0 · 生效日期 2026-11-07 · 适用于 `allocation-java` 全部代码与全部贡献者（含 AI）**

---

## 序言

这个组件的存在意义，不是"能算分摊"，而是**任何人在任何时候，都能证明某一块钱的去向是对的**。

因此本项目的最高优先级排序是：

> **可证明 > 正确 > 可维护 > 性能 > 便利**

任何一次提交，只要破坏了上面这个顺序，即便它"跑得更快""代码更短"，也一律拒绝。

以下 15 条为**不可协商条款**。违反任一条的 PR，无论功能多完整，直接阻断合并。

---

## 第一条 内核必须不认识 Spring

`allocation-kernel` 模块的 `pom.xml` 中**禁止**出现 `spring-*`、`mybatis-*`、`jakarta.persistence`、`redis`、`kafka` 等任何框架依赖。

依赖方向永远单向：

```
spring-boot-starter  →  kernel
        ✗  反向依赖一律拒绝
```

**理由**：内核必须能在 `@Test` 里三行代码跑完，必须能塞进任何运行时。这是它"经得起历史考验"的唯一物理保障。

**验证方式**：`mvn -pl allocation-kernel dependency:list` 的产出中无第三方框架。CI 内置检查。

---

## 第二条 金额只用 `long` 缩放整数

- 内核中金额类型**只有** `long`（以 10^precision 为最小单位）。
- 禁止 `double` / `float` / `Double` / `Float` 出现在任何金额计算路径。
- `BigDecimal` 只允许出现在**边界适配层**（HTTP 请求、DB 映射、CSV 解析的入口与出口），进入内核前必须转换为 `long`。
- 精度只允许 `0..6`。超出必须拒绝，**不允许四舍五入到合法精度**。

**验证方式**：ArchUnit 规则禁止 `java.lang.Double`/`Float` 出现在 `..kernel..` 包；Code Review 检查边界转换点。

---

## 第三条 每一次算术都必须证明不溢出

裸写 `a * b`、`a + b` 即为缺陷，包括"我知道不会溢出"的情况。

- 加法：`Math.addExact` / `Math.subtractExact`
- 乘法：`Math.multiplyHigh` 判定，或退化为 `BigInteger`
- 分母累加：`BigInteger`（权重之和可能超过 `long`）
- 溢出 → 抛业务异常，**绝不回绕**

**理由**：`long` 溢出是静默的。一个回绕的负数金额，会在财务上表现为"某一方被倒扣"，而所有守恒校验都可能仍然通过。

---

## 第四条 除法只允许"整除 + 余数显式分配"

禁止 `total / n` 直接得到金额。

唯一合法形态：`Apportion`（见 `SEMANTICS.md` §2），即整除求商、显式收集余数、按确定性规则分配残余。

**禁止**：`Math.round`、`setScale(HALF_UP)`、任何形式的"每份四舍五入再求和"。实测 100 万行会产生 +329 元（double）或 +995 元（整数各自舍入）的漂移。

---

## 第五条 尾差归属必须确定、且与输入顺序无关

平局裁决只看**业务身份**（目标完整坐标的规范键），永远不看：

- 输入文件的行序
- `HashMap` 的遍历序
- 线程完成顺序
- 数据库返回顺序

**验证方式**：属性测试——同一批数据做任意置换，输出必须逐字节相同。

---

## 第六条 并行只允许发生在池级

- 并行单位 = 一个池（pool）。
- 池内计算必须单线程完成。
- 输出合并必须**有序**：按池键升序收集。
- **禁止** `parallelStream().forEach(...)` 写共享状态；**禁止**任何依赖完成顺序的累加。

**理由**：分摊的确定性比吞吐重要一个数量级。8 线程只带来 1.6 倍提升（实测），但不确定性会带来无穷的排查成本。

---

## 第七条 每个池必须守恒断言，失败必须 fail-closed

- 每个池分摊后断言 `output == poolTotal`。
- 全局断言 `grandTotal == inputTotal`。
- `immutable_dimensions` / `conservation_keys` 必须逐成员校验未被改写。
- 任何断言失败 → 整个运行 `FAILED`，**不发布任何结果、不写任何半成品**。

"部分成功"在这个系统里不存在。

---

## 第八条 结果发布必须原子且幂等

- 幂等键：`hash(ruleSnapshotId + inputFingerprint + engineVersion)`，数据库唯一索引。
- 同一幂等键重复提交，返回**同一次运行**的结果，不重算、不产生第二份数据。
- 明细先以 `run_id` 写入，全部成功后用一个**单条小事务**把 run 从 `RUNNING` 翻转为 `PUBLISHED`。
- 发布后的结果**只读**，任何修改必须产生新 run。

**禁止**：先删后插、原地更新已发布结果、跨 run 复用明细行。

---

## 第九条 每一分钱都必须可解释

每条输出行必须能回答四个问题：

1. 来自哪个池（上游坐标）
2. 除以多少（权重分子 / 分母）
3. 余数是几、为什么给了它（最大余数排名）
4. 依据哪一版规则（规则快照 SHA-256）

做不到这一点的实现，功能再对也不算完成。`Explain` 接口是本条的物化。

---

## 第十条 变更顺序不可颠倒

任何行为变更，必须按此顺序：

```
1. 修改 docs/SEMANTICS.md    （PR 标题带 [SEMANTICS]）
2. 修改/新增黄金语料                    （带期望输出的 .golden 文件）
3. 修改代码
4. 差分测试全绿
5. 更新 CHANGELOG
```

跳过第 1 步直接改代码的 PR，一律打回。**规格先行不是为了流程好看，是因为这个系统里"意图"和"实现"必须能分别审计。**

---

## 第十一条 差分测试是唯一验收标准

- 覆盖率不是标准，行数不是标准，"看起来对"不是标准。
- 唯一标准：**黄金语料全绿 + 属性测试全绿**。
- 新增任何金额逻辑，必须新增对应语料；语料只能新增，不能为了让测试通过而修改既有期望值。
- 修改既有期望值 = 变更行为 = 走第十条。

---

## 第十二条 性能优化必须证明金额不变

任何优化 PR 必须附带：优化前后**同一语料的输出逐字节比对结果**。

禁止的"优化"举例：

- 把 `long` 换成 `double` 提速
- 用 `parallelStream` 替代有序收集
- 缓存分摊结果跳过重算（除第八条的幂等外）
- 用近似算法替代精确余数分配

---

## 第十三条 不移植工作台，只提供能力

前端、菜单、报表页、可视化实验室**不在本项目范围**。

本项目只交付：内核 + Spring Starter + REST 契约 + DDL + 测试。宿主工程（若依）用它的代码生成器和权限体系自己长页面。

**理由**：一旦开始写页面，内核就会被业务细节污染，三年后无法维护。

---

## 第十四条 不引入"顺手"的抽象

禁止为了"扩展性"提前引入：

- 自研表达式引擎（规则已是 JSON DSL）
- 插件热加载
- 多引擎适配层（"以后可能换算法"）
- 通用图计算框架

规则 DSL 是唯一扩展点。新增能力优先扩展 DSL 字段，其次新增阶段类型，**最后**才考虑新接口。

---

## 第十五条 文档与代码同权重

以下情况视为**功能未完成**：

- `SEMANTICS.md` 未同步
- 新增配置项未写入 `docs/API.md`
- 新增错误码未登记
- 迁移/兼容说明缺失

---

## 附：每个 PR 的自检清单（AI 必须逐条执行）

在提交前，逐条回答，任何一条为"否"则不许提交：

1. [ ] 金额路径上有没有出现 `double`/`float`？
2. [ ] 有没有裸的 `*` 或 `+` 作用于金额/权重？
3. [ ] 除法是否全部通过 `Apportion`？
4. [ ] 平局裁决是否只依赖业务身份？
5. [ ] 并行是否只发生在池级，且输出有序？
6. [ ] 每个池是否有守恒断言，失败是否 fail-closed？
7. [ ] 新行为是否先改了 `SEMANTICS.md`？
8. [ ] 是否新增了对应黄金语料？
9. [ ] 差分测试是否全绿（L1 + L2）？
10. [ ] 内核模块是否仍然零框架依赖？
11. [ ] 是否更新了 CHANGELOG 与错误码表？
12. [ ] 有没有为了"以后可能用到"而新增抽象？

---

## 修订程序

- 本宪法只能通过**显式提案**修改：PR 标题 `[CONSTITUTION] 提案：<条款> <变更>`。
- 提案必须包含：违反现状的具体案例、不改的后果、改后的代价。
- 条款编号一旦发布不得复用；废弃条款保留并标注 `DEPRECATED`。

---

> 写在最后：这份宪法的每一条，都对应一个真实会让人赔钱或赔信誉的场景。
> 当你觉得某一条"太严格了，这次先放过"的时候，请回想它是为什么被写下来的。
